Como vimos en clases anteriores, una aplicación web necesita diferentes tecnologías con responsabilidades claras:

- **HTML** se encarga de describir el contenido y su estructura.
- **CSS** se encarga exclusivamente de la presentación visual y los estilos.
- **JavaScript** se encarga del comportamiento en el navegador.

Aquí es donde entra **Angular**: Angular es un *framework* para construir aplicaciones web, el cual intenta unir las responsabilidades de cada tecnología típica.

A pesar de que no hay problema con usar JavaScript, y que por sí solo puedes construir casi cualquier cosa, este no te impone un orden. Un *framework* como Angular proporciona una estructura común, como piezas que ya están organizadas y coordenadas, lo que evita que cada programador "reinvente la rueda".

Angular trae herramientas clave como los **componentes** y **templates**, los cuales se encargan de construir la interfaz de usuario de manera modular. Además tenemos los **Signals**, los cuales manejan el estado de la aplicación de forma "reactiva", es decir, la pantalla se actualiza sola cuando un dato cambia. También tenemos los **servicios e inyección de dependencias**, cuyo objetivo es que distintas partes de la app puedan compartir lógica sin enredar el código. Finalmente tenemos los **Routers**; su trabajo es simplemente manejar la navegación entre distintas pantallas.

La principal característica de Angular es que se utiliza para crear interfaces que corren completamente en el navegador. En desarrollo HTML tradicional, cada vez que haces click a un enlace tu navegador le pide un documento HTML nuevo al servidor; esto hace que la página actual se destruya y se reemplace por ese HTML solicitado.

La diferencia con Angular es que está orientado al **SPA** (*Single Page Application*), el cual carga el documento inicial de la app una sola vez. A partir de ahí, cuando haces clic en un enlace interno, el **Angular Router** lee la dirección URL y simplemente cambia el componente visual que estás viendo. El servidor solo se encarga de entregar los recursos básicos. Esto hace que la app se sienta instantánea, pero manteniendo la capacidad de usar los botones atrás y adelante del navegador.

### Templates y Bindings

Un **Template** en Angular no es solo un HTML estático; el *framework* reconoce expresiones y *"bindings"* (enlaces) dentro de él. Para esto existen tres formas principales de enlazar la interfaz con la lógica:

- **Interpolación**: Se escribe con dobles llaves `{{ title }}` y sirve para insertar un valor de tu clase directamente como texto en la pantalla.
- **Binding de propiedad**: Se encierra entre corchetes `[class.is-complete]="completed"`, el cual le entrega un valor de la clase a una propiedad de un elemento HTML.
- **Binding de evento**: Se encierra entre paréntesis `(click)="greet()"`, el cual conecta una interacción de usuario con una acción o método de la clase.

La ventaja es que no necesitas buscar nodos en el DOM para reescribirlos manualmente; Angular los evalúa por ti cuando los datos cambian.

### Ciclo de vida de un Componente

Cada vez que Angular crea un componente en la pantalla, este pasa por un ciclo de vida: Angular lo crea, prepara sus entradas, actualiza su vista y finalmente lo destruye cuando no se usa. Nosotros podemos intervenir en ese proceso mediante *"hooks"*:

- **Constructor**: No es un *hook* de Angular; es una función de la clase TypeScript que se ejecuta al instanciarla. Sirve para establecer dependencias o valores básicos.
- `fn::ngOnInit()`: Se ejecuta una sola vez después de que Angular configura las entradas iniciales. Sirve para preparaciones que dependen de esos datos de entrada.
- `fn::ngOnChanges(changes)`: Se ejecuta cuando el componente padre modifica las propiedades de entrada de este componente.
- `fn::ngAfterViewInit()`: Ocurre una vez cuando los elementos del *template* propio ya se inicializaron.
- `fn::ngOnDestroy()`: Se ejecuta justo antes de que el componente sea destruido (por ejemplo, si cambias de pantalla). Es vital para liberar recursos, como temporizadores o suscripciones que abriste manualmente.

Anteriormente se mencionó que nuestra aplicación era *"standalone"*; esto es importante ya que antiguamente las dependencias se escribían en un archivo global usando `@NgModule`. En este curso se utiliza la forma moderna llamada *"standalone"*, donde cada componente declara directamente lo que usa en sus `attr::imports`.

## Control de flujo y listas

Las interfaces reales no muestran un solo objeto fijo, sino que representan colecciones de datos y estados vacíos. El control de flujo en Angular determina qué fragmentos del *template* aparecen en pantalla. Para esto Angular utiliza bloques específicos en el *template* para manejar la lógica de presentación:

- `@if` actúa como el típico `kw::if` de código: incorpora contenido cuando se cumple una condición.
- `@for` actúa como el `kw::for` de código normal: repite un bloque de código para cada elemento dentro de una colección.
- `@empty` ofrece una alternativa visual cuando la colección del `@for` no tiene elementos.
- `@switch` funciona como el típico `kw::switch` de código: permite elegir entre varias alternativas excluyentes.

## Signals

El **estado** es la información que puede cambiar durante el uso de la aplicación, como nuestra lista de tareas. La **reactividad** es el sistema que permite saber qué partes de la interfaz dependen de ese estado; de este modo, cuando los datos cambian, Angular actualiza automáticamente las vistas que los leyeron. Aquí es donde entran las **Signals**.

Las **Signals** son un sistema integrado en Angular las cuales se encargan de manejar los datos reactivos de manera óptima; se incluyen en código mediante diversas funciones:

- `fn::signal(valor)` crea una señal "escribible". Para leer su valor actual en cualquier momento, simplemente se invoca como una función cualquiera, por ejemplo `fn::tasks()`.
- `fn::set(valor)` reemplaza el valor actual de la señal.
- `fn::update(fn)` calcula un nuevo valor basándose en el valor actual, lo cual es ideal para modificar arreglos o listas.
- `fn::computed(fn)` crea una señal de solo lectura que deriva su resultado matemática o lógicamente de otras señales. Angular memoriza este resultado y solo lo recalcula si alguna de sus dependencias cambia.

Ahora utilicemos Signals para refactorizar nuestra lista: empezaremos por convertir nuestro arreglo estático a una señal y añadiremos una señal calculada (`fn::computed`) para saber cuántas tareas nos faltan. En `task-list.ts`:

```ts title="src/app/task-list/task-list.ts" del={1, 11} ins={2, 12-16, 18-28}
import { Component } from '@angular/core';
import { Component, computed, signal } from '@angular/core';
import { Task } from '../models/task';

@Component({
  selector: 'app-task-list',
  standalone: true,
  templateUrl: './task-list.html'
})
export class TaskList {
  readonly tasks: Task[] = [
  // Convertimos el arreglo en una Signal escribible
  readonly tasks = signal([
    { id: 1, title: 'Revisar componentes', description: 'Leer la tarjeta.', completed: true, priority: 'media' },
    { id: 2, title: 'Practicar Signals', description: 'Cambiar un estado.', completed: false, priority: 'alta' }
  ]);

  // Señal calculada: se actualiza sola si 'tasks' cambia
  readonly pending = computed(() =>
    this.tasks().filter(task => !task.completed)
  );

  toggle(id: number): void {
    this.tasks.update(items => items.map(task =>
      task.id === id ? { ...task, completed: !task.completed } : task
    ));
  }
}
```

Utilizamos `fn::computed` para que la señal se actualice sola si acaso `var::tasks` cambia. Dentro de la función `fn::toggle()` utilizamos `fn::map()` para crear un arreglo nuevo y la sintaxis de propagación `{...task}` para crear un objeto nuevo exclusivamente para la tarea modificada. Esta actualización "inmutable" le entrega a la Signal un valor de referencia completamente nuevo, dejando claro qué fue lo que cambió. Si modificáramos el dato directamente, la Signal no notificaría el cambio y la pantalla quedaría desactualizada.

Actualizamos `task-list.html` con `fn::tasks()` y `fn::pending()` para que Angular registre automáticamente que este *template* depende de esas señales:

```html title="src/app/task-list/task-list.html" del={3} ins={1, 4, 11-13}

@for (task of tasks; track task.id) {
@for (task of tasks(); track task.id) {
  <article>
    <h2>{{ task.title }}</h2>
    <p>{{ task.description }}</p>
    <p>Prioridad: {{ task.priority }}</p>

    <p>{{ task.completed ? 'Completada' : 'Pendiente' }}</p>

      {{ task.completed ? 'Reabrir' : 'Completar' }}
    </button>
  </article>
} @empty {
  <p>No hay tareas.</p>
}
```

Anteriormente creamos el proyecto con el tag `--zoneless` y se mencionó que era para las Signals. Antiguamente Angular utilizaba **Zone.js**, el cual observaba todos los eventos del navegador y suponía cuándo debía revisar las vistas para ver si algo había cambiado. A partir de Angular 21, la configuración por defecto es *"zoneless"*.

En Angular también verás a menudo la librería **RxJS**. Es vital no confundir ambas herramientas, ya que resuelven problemas distintos:

- **Signals**: Representan un *valor actual* que se puede consultar de forma síncrona. Son ideales para manejar el estado local o compartido de la interfaz.
- **Observables (RxJS)**: Representan una *secuencia de eventos* a lo largo del tiempo. Son ideales para coordinar eventos asíncronos, como solicitudes HTTP al servidor o flujos de datos complejos.

## Comunicación entre Componentes

Cuando una pantalla contiene varias piezas, hace falta un acuerdo claro sobre quién conserva los datos y quién solo los presenta. En lo que hemos visto, nuestra `cls::TaskList` es el componente padre que posee la colección y decide cómo cambiarla, mientras que `cls::TaskCard` es el componente hijo que recibe una tarea, la representa y comunica la acción que solicita el usuario.

Esta separación de responsabilidades permite que la tarjeta sea reutilizable y mantiene la modificación de la lista en un único lugar. Angular nos proporciona dos herramientas modernas para la comunicación de componentes:

- `fn::input()` declara los datos que el padre le entrega al hijo. Un *input* requerido se declara con `input.required<Task>()` y su valor se convierte en una Signal de solo lectura dentro del hijo.
- `fn::output()` declara los eventos que el hijo emite hacia el padre. El padre lo escucha usando un *binding* de evento y recibe su valor a través de la variable `var::$event`.

Vamos a modificar nuestra `cls::TaskCard` para que ya no tenga datos fijos, sino que reciba la tarea desde afuera y emita una intención al hacer clic en el botón:

```ts title="src/app/task-card/task-card.ts" del={1, 9, 12-13} ins={2-3, 14-15}
import { Component } from '@angular/core';
import { Component, input, output } from '@angular/core';
import { Task } from '../models/task';

@Component({
  selector: 'app-task-card',
  standalone: true,
  templateUrl: './task-card.html',
  styleUrl: './task-card.css'
})
export class TaskCard {
  title = 'Preparar el proyecto';
  completed = false;
  readonly task = input.required<Task>();
  readonly toggleRequested = output<number>();
}
```

Y también su HTML:

```html title="src/app/task-card/task-card.html" del={1-3} ins={4-13}
<article [class.is-complete]="completed">
  <h2>{{ title }}</h2>
  <p>{{ completed ? 'Completada' : 'Pendiente' }}</p>
<article [class.is-complete]="task().completed">
  <h2>{{ task().title }}</h2>
  <p>{{ task().description }}</p>
  <p>Prioridad: {{ task().priority }}</p>

  <p>{{ task().completed ? 'Completada' : 'Pendiente' }}</p>

  <button type="button" (click)="toggleRequested.emit(task().id)">
    {{ task().completed ? 'Reabrir' : 'Completar' }}
  </button>
</article>
```

Ahora leemos la tarea invocando `fn::task()` porque el *input* moderno de Angular se comporta como una Signal. Al pulsar el botón, la tarjeta no cambia el estado por sí sola; simplemente emite el identificador `task().id` hacia el exterior.

## Inyección de dependencias

Hasta ahora guardar la colección de tareas dentro de `cls::TaskList` era razonable porque era el único lugar que la usaba, pero ¿qué pasa cuando agreguemos una vista de "Detalle de Tarea"? Si cada componente guarda su propia copia de la lista, completar una tarea en la lista principal dejará obsoleta la copia del detalle.

Es para esto que existe la **Inyección de Dependencias**: con esto, en lugar de que cada componente construya el servicio manualmente usando `new TaskStore()`, Angular utiliza la inyección de dependencias. Esto significa que el componente simplemente declara "necesito este servicio" y Angular busca el proveedor, crea la instancia o incluso reutiliza una ya existente, y luego se la entrega.

Existen dos formas de pedir un servicio: a través de un parámetro en el constructor o mediante la función `fn::inject()`.

Primero vamos a crear nuestro nuevo servicio `cls::TaskStore`; para eso vamos a ejecutar el siguiente comando:

```bash
ng generate service services/task-store --skip-tests
```

Y reemplazaremos el código del archivo `task-store.ts` creado por este:

```ts title="src/app/services/task-store.ts"
import { Service, signal } from '@angular/core';
import { Task, Priority } from '../models/task';

@Service()
export class TaskStore {
  // Señal privada escribible: solo el servicio puede modificarla
  private readonly taskState = signal<Task[]>([
    { id: 1, title: 'Revisar componentes', description: 'Identificar template...', completed: true, priority: 'media' },
    { id: 2, title: 'Practicar Signals', description: 'Completar una tarea...', completed: false, priority: 'alta' }
  ]);

  // Señal pública de solo lectura: los componentes la leen, pero no la pueden sobreescribir
  readonly tasks = this.taskState.asReadonly();

  toggle(id: number): void {
    this.taskState.update((items) => items.map((task) =>
      task.id === id ? { ...task, completed: !task.completed } : task
    ));
  }

  remove(id: number): void {
    this.taskState.update((items) => items.filter((task) => task.id !== id));
  }

  find(id: number): Task | undefined {
    return this.tasks().find((task) => task.id === id);
  }
}
```

Aquí utilizamos el decorador `@Service()` introducido en Angular 22.1, el cual registra este servicio en la raíz de la aplicación, garantizando que todos los componentes compartan la misma instancia exacta.

Ahora vamos a limpiar `cls::TaskList` para que ya no guarde tareas ni la lógica de `fn::toggle`; simplemente se conectará al servicio mediante `inject(TaskStore)`:

```ts title="src/app/task-list/task-list.ts" del={1-2, 14-24} ins={3-7, 11, 25-46}
import { Component, computed, signal } from '@angular/core';
import { Task } from '../models/task';
import { Component, computed, inject, signal } from '@angular/core';
import { TaskCard } from '../task-card/task-card';
import { TaskStore } from '../services/task-store';

type TaskFilter = 'todas' | 'pendientes';

@Component({
  selector: 'app-task-list',
  standalone: true,
  imports: [TaskCard],
  templateUrl: './task-list.html'
})
export class TaskList {
  readonly tasks = signal([
    { id: 1, title: 'Revisar componentes', description: 'Leer la tarjeta.', completed: true, priority: 'media' },
    { id: 2, title: 'Practicar Signals', description: 'Cambiar un estado.', completed: false, priority: 'alta' }
  ]);
  readonly pending = computed(() =>
    this.tasks().filter(task => !task.completed)
  );
  toggle(id: number): void {
    this.tasks.update(items => items.map(task =>
      task.id === id ? { ...task, completed: !task.completed } : task
    ));
  }
  // Inyectamos el servicio
  readonly store = inject(TaskStore);

  readonly filter = signal<TaskFilter>('todas');

  // Ahora leemos las tareas directamente desde store.tasks()
  readonly pendingCount = computed(() =>
    this.store.tasks().filter(task => !task.completed).length
  );

  readonly visibleTasks = computed(() =>
    this.filter() === 'pendientes'
      ? this.store.tasks().filter(task => !task.completed)
      : this.store.tasks()
  );

  setFilter(event: Event): void {
    const value = (event.target as HTMLSelectElement).value;
    this.filter.set(value === 'pendientes' ? 'pendientes' : 'todas');
  }
}
```

Y también actualizaremos su HTML para que llame directamente al servicio en lugar de una función local:

```html title="src/app/task-list/task-list.html" del={4} ins={5}
@for (task of visibleTasks(); track task.id) {
  <app-task-card
    [task]="task"
    (toggleRequested)="toggle($event)" />
    (toggleRequested)="store.toggle($event)" />
}
```

El detalle debe leer la URL para saber qué tarea mostrar. Para ello inyectaremos `cls::ActivatedRoute` (para leer el parámetro variable `:id`) y el `cls::TaskStore` (para buscar la tarea en la única fuente de verdad) en `task-detail.ts`:

```ts title="src/app/task-detail/task-detail.ts"
import { Component, inject } from '@angular/core';
import { ActivatedRoute, RouterLink } from '@angular/router';
import { TaskStore } from '../services/task-store';

@Component({
  selector: 'app-task-detail',
  standalone: true,
  imports: [RouterLink],
  templateUrl: './task-detail.html'
})
export class TaskDetail {
  private readonly route = inject(ActivatedRoute);
  private readonly store = inject(TaskStore);

  get task() {
    const value = this.route.snapshot.paramMap.get('id');
    const id = value === null ? Number.NaN : Number(value);
    return Number.isInteger(id) ? this.store.find(id) : undefined;
  }
}
```

En su HTML usaremos `@if` para mostrar la tarea si acaso existe; si no existe o se ingresó un ID inválido, se enviará un error mediante `@else`:

```html title="src/app/task-detail/task-detail.html"
@if (task; as item) {
  <article>
    <p>Detalle de tarea, #{{ item.id }}</p>
    <h1>{{ item.title }}</h1>
    <p>{{ item.description }}</p>
    <p>Estado: {{ item.completed ? 'Completada' : 'Pendiente' }}</p>
    <a routerLink="/tareas">Volver a tareas</a>
  </article>
} @else {
  <section>
    <h1>No encontramos esa tarea</h1>
    <a routerLink="/tareas">Volver a tareas</a>
  </section>
}
```

## Resumen Final

Si quedaste muy perdido leyendo el código, puedes leer este resumen y volver a cada sección para entenderlo mejor.

El objetivo del proyecto fue crear una aplicación web tipo **SPA** (la página entera no se actualiza con cada acción) que nos permite organizar pendientes como tareas. En ella podemos ver una lista de tareas, agregar nuevas, marcarlas como completadas, filtrarlas y entrar a ver detalles específicos de cada una. Para lograr esto separamos el proyecto por partes:

### Los datos (molde)

Nuestro modelo de tarea `cls::Task`: simplemente es un contrato, así como una interfaz de programación. Lo hicimos para obligarnos a que toda tarea tenga siempre un título, descripción, identificador, estado y prioridad, con el objetivo de ahorrarnos errores de escritura en los datos.

### El cerebro central (Servicio)

Nuestro `cls::TaskStore` es la única fuente de verdad. La creamos para centralizar la lista real de tareas y las acciones que las modifican. Lo hicimos porque, como la pantalla de Lista y la pantalla de Detalle necesitan ver las mismas tareas, tener este servicio evita que los datos se desincronicen entre ellas.

### El marco y el Tráfico (Navegación)

La `cls::App` es nuestro componente raíz; es el marco principal de toda la aplicación. Lo usamos para poner el menú superior de navegación y un espacio vacío (el `cls::RouterOutlet`) donde van entrando y saliendo las demás pantallas.

El **Router** es nuestra policía de tránsito. Su trabajo es leer la dirección URL y decidir qué pantalla debe dibujarse dentro del componente `cls::App`. Gracias a él podemos tener enlaces directos a pantallas específicas sin recargar el navegador.

### Las pantallas (vistas de página)

- `cls::Home` es nuestra pantalla de inicio, muy sencilla, cuya única función es dar la bienvenida y ofrecer un enlace para ir a organizar las tareas.
- `cls::TaskList` es el componente coordinador (el padre). Su trabajo es leer las tareas desde el `cls::TaskStore`, manejar el filtro local y dibujar una "Tarjeta" por cada tarea visible.
- `cls::TaskDetail` es la pantalla de enfoque. Su trabajo es leer el ID que viene en la URL de navegación, ir a buscar esa tarea específica al `cls::TaskStore` y mostrar toda su información detallada.

### Piezas visuales reutilizables

`cls::TaskCard` es el componente hijo y su única responsabilidad es la presentación. Recibe una tarea individual desde afuera (mediante `fn::input`) y la dibuja de forma bonita en pantalla; si el usuario hace clic en un botón, emite un aviso (mediante `fn::output`) hacia el padre. No guarda ni modifica datos por sí solo.

### La magia del framework

Las **Signals** son el mecanismo interno que envuelve nuestros datos para hacerlos "reactivos". Las usamos para que, cuando el `cls::TaskStore` cambie un dato, Angular se dé cuenta instantáneamente y actualice sola la pantalla, sin que nosotros tengamos que decirle qué botón o texto cambiar.
